## 一、系统定位与使命

`WZCityTCDS` 定位为**城市时空可信内容枢纽（City Spatial-Temporal Trusted Content Hub）的正式事实出版内核（Formal Fact Publication Kernel）**。

### 1.1 核心使命
- 面向城市地理与时空语境（GEO Context），建立端到端受控、可核验、可引用的结构化事实生产与不可变出版体系；
- 将分散的上游新闻报道、政务公告与权威信源语料，经由采集过滤、事实抽取、人工仲裁审核、冲突消解与正式签发流程，转化为权威、无歧义、具备证据链条的结构化事实记录；
- 独占事实发布、更正、撤回与版本追溯的受控写生命周期，为全域知识消费、公众页面与机器出口提供唯一的官方出版快照。

### 1.2 架构否定项（Anti-Patterns）
- **禁止建立平行实体主数据**：本系统不作为独立的平行事实或实体权威，不另行维护一套与枢纽脱节的城市实体库；
- **禁止无证据的自由生成**：模型抽取与辅助推断仅作为初筛候选，严禁无精确原文证据锚点的模型幻觉事实直接入库或签发；
- **禁止原地覆盖与静默修改**：已签发事实的历史版本永久不可变，禁止任何形式的物理覆盖更新。

## 二、实体主数据单根归属（Single Root of Entity Identity）

实体身份的唯一性与稳定性是事实权威的前提。本系统严格遵循“实体单根归口”原则：

```
+--------------------------------------------------------------+
|            城市时空可信内容枢纽 (Trusted Content Hub)            |
|  - 拥有 Entity ID / Canonical Name 权威治理权                  |
|  - 统一维护 实体别名 (Alias) 与 实体重定向 (Redirect)           |
|  - 负责 全域知识图谱拓扑与时空坐标挂载                            |
+------------------------------+-------------------------------+
                               |
                   实体身份解析 | 单向受控投影
                   (Entity Query) (Published Facts)
                               |
+------------------------------v-------------------------------+
|             WZCityTCDS (事实出版内核 / Publication Kernel)      |
|  - 消费标准 Entity ID，不新建实体主表                            |
|  - 维护基于 Entity ID 的事实断言 (FactAssertion) 与版本链        |
|  - 产生 事实候选、人工审核、版本链、出版快照与机器出口            |
+--------------------------------------------------------------+
```

### 2.1 实体归口契约
1. **主身份归口**：城市实体、实体类型（POI、机构、行政区划、历史事件、地理单元等）、实体别名及重定向关系，全部归口于枢纽主数据服务；
2. **本系统角色**：WZCityTCDS 内部仅存储实体在枢纽中的规范标识符（`entity_id`）作为外键或引用锚点，不建立可自由新增、修改实体属性的平行主表；
3. **发现新实体处理规程**：
   - 当抽取管道识别到枢纽尚未收录的新实体线索时，系统仅在审核工作流中标记为待收录候选实体引用（`unresolved_entity_ref`）；
   - 必须通过接口向枢纽提交实体治理提案，待枢纽正式分配 `entity_id` 并确认其规范名称后，方可完成事实签发绑定。

## 三、逻辑主记录与单向受控投影机制（One-Way Controlled Projection）

系统间数据流转严格遵循“权责独占、单向受控投影”机制，杜绝双向循环同步引发的数据脑裂。

### 3.1 领域责任划分矩阵

| 领域对象 / 能力 | 归属主体 | 治理责任与权限 |
| :--- | :--- | :--- |
| **城市实体 (Entity) / 别名 (Alias)** | 城市时空可信内容枢纽 | 权威主数据，负责唯一身份标识与时空拓扑 |
| **信源语料原文 (Source News)** | 上游 CMS / 权威发布平台 | 原文版权与原始采编事实责任 |
| **候选抽取 (Candidate Extraction)** | WZCityTCDS 内部管道 | 自动化算法流水线，内部暂存，不对外暴露 |
| **审核任务 (ReviewTask)** | WZCityTCDS 审核工作台 | 人工审校、合规确认与质量仲裁 |
| **事实断言与版本 (FactAssertion / Revision)** | WZCityTCDS 独占 | 独占写入口，不可变版本链管理 |
| **出版快照 (Publication / Revision)** | WZCityTCDS 独占 | 权威签发、更正、撤销与对外出版出口 |
| **证据片段 (EvidenceSpan)** | WZCityTCDS 绑定存证 | 字符级证据锚点、哈希指纹与原文映射 |
| **全域检索与下游应用集成** | 城市时空可信内容枢纽 | 消费 WZCityTCDS 单向投影事实，无权逆向改写 |

### 3.2 单向受控投影规则
1. **独占写控制**：WZCityTCDS 拥有对事实断言（`FactAssertion`）与出版物（`Publication`）的排他性写入与版本管理权限；
2. **事件驱动投影**：每当完成事实签发（`PUBLISHED`）、更正（`CORRECTED`）或撤回（`REVOKED`），系统通过不可变事件总线或安全快照，单向向枢纽推送已签发的事实投影数据；
3. **枢纽只读消费**：枢纽作为全域知识检索与上层业务支撑方，仅能只读消费上述投影事实，严禁在枢纽侧绕过 WZCityTCDS 对事实内容进行直接篡改或状态逆向回写。

## 四、事实版本链与不可变出版约束（Immutable Revision Chain）

事实数据的可信度来自于每一个断言都有迹可查、版本永久可溯。

### 4.1 Append-Only 版本链
- 事实的每次状态流转或内容变更，必须生成全新的递增版本号（`FactRevision`）；
- 每次修订记录包含完整的修订原因、操作人（审计角色）、前序版本 SHA-256、证据哈希及时间戳；
- 严禁任何数据库物理删除（`DELETE`）或非版本化更新（`UPDATE`）已发布事实。

### 4.2 严格区分三种生命周期操作
1. **事实更正 (Fact Correction)**：
   - 场景：原发布事实中存在数字、时间、地点等事实性偏差；
   - 动作：保留原版本，生成新版本并显式关联更正声明（`correction_notice`），更新对外指向至新版本；
2. **事实撤回 (Fact Revocation)**：
   - 场景：原发布事实被证实完全失实或存在严重合规风险；
   - 动作：发布撤回墓碑标记（Tombstone Record），保留审计历史与撤回原因，公共页面展示撤回声明并切断常规引用；
3. **上游撤稿 (Upstream Source Retraction)**：
   - 场景：上游 CMS 删除了某篇源报道；
   - 动作：自动触发事实影响面评估，根据证据独立性原则重新评定事实质量状态（若该事实失去唯一证据支撑，则进入复审或挂起状态），不得静默连带抹除历史发布记录。

### 4.3 证据溯源规约（EvidenceSpan Integrity）
- 每一个结构化属性断言，必须绑定至少一个精确的 `EvidenceSpan`；
- `EvidenceSpan` 必须包含：
  - 来源文档权威标识（`source_doc_id`）；
  - 精确字符定位（`char_start`, `char_end`）；
  - 引用原文片段（`quoted_text`）；
  - 原文片段 SHA-256 哈希值（`span_hash`）；
- 校验器在出版签发时，必须依据原始语料对 `span_hash` 进行确定性验签，杜绝篡改。

## 五、消费出口与安全边界（Public Outlets & Security Boundary）

### 5.1 出口统一消费准则
所有面向公众与下游系统的出口，包括但不限于：
- HTML 前端档案页与详情页；
- 开放 RESTful API；
- 结构化 JSON-LD 事实卡片；
- RSS / Atom 订阅源；
- XML Sitemap 与 变更流（Changes API）；
- 大模型检索增强（MCP / RAG Tool Endpoints）；

**强制红线：上述所有出口只能读取并消费处于 `PUBLISHED` 状态的不可变签发版本（PublicationRevision）。**

### 5.2 隔离沙箱与防泄漏
- `DRAFT`（草稿）、`CANDIDATE`（候选提取物）、`UNDER_REVIEW`（待审核）、`REJECTED`（已驳回）等中间态数据，全部限制在受控内部工作区；
- 严禁任何公网出口向非授权用户暴露未经签发的事实候选；
- 严格执行公开内容安全扫描，确保不包含内网 IP、开发调试接口、私有凭据与未脱敏隐私数据。

## 六、实施与演进路线

基于本 Option A 架构边界，后续业务切片开发严格按以下顺序演进：
1. **S2（实体与信源接入契约）**：定义与枢纽 `EntityResolver` 及 CMS 语料接入的确定性 JSON Schema 与 API 契约；
2. **S3（事实版本链与不可变签发内核）**：落地 `FactRevision`、`PublicationRevision` 状态机与审计链；
3. **S4（EvidenceSpan 证据验签引擎）**：落地字符级证据提取、`span_hash` 计算与一致性校验；
4. **S5（机器出口与统一发布门禁）**：实现 Feed、Changes、MCP 与发布安全门禁。
